## 一粒种子的自白

规范是承诺，实现是兑现。Lodestone Protocol v1.3 Final 用数千字钉死了节点、边、状态机与容错分层，但规范文本本身不能回答"这个文档解析出来到底是什么"——能回答的只有解析器。若解析器散落在各消费方手中各自诠释，规范就退化为一厢情愿；若只有一个权威实现，且其每一条行为都被测试钉死，规范才真正落地。

lodestone-md 就是这个权威实现。它生来肩负三件事：**兑现**（严格实现 v1.3 的全部 MUST）、**验证**（Golden Fixture 让每条规则成为可执行断言）、**演进**（v2.0 议程的试验基地与反馈源头）。

协议的灵魂是确定性：解析输出是文档当前字节的纯函数。这条原则贯穿实现的每一层——无全局状态、固定输出序、依赖图锁定（Cargo.lock 入库）。任何引入非确定性的改动（哈希顺序遍历、时间依赖、浮点聚合）都是对身份的背叛。

协议的第二灵魂是按需加载：L1 骨架（节点表 + 边 + 诊断）让消费方以极低成本重建全局认知，L2 定点正文（body_start/body_end）按需取证，L3 全文仅留给查全率任务。解析器的输出契约（§8.1–§8.4）正是为这一读取模式设计的：骨架完整、正文可寻址。

## 一、完整初心（解析管线）

规范 §8 钉死了 10 步管线，实现将其物化为单一数据流（ADR-0001）：

| 步 | 规范依据 | 实现模块 | 输出 |
|---|---|---|---|
| 1 | §4.1 节点切分 | comrak 顶层块扫描 | 节点物理行区间 |
| 2 | §3.1 文档级元数据 | 行级提取 + JSON 预扫 | doc_meta 或警告 |
| 3 | §5 元数据三层校验 | 形态层/JSON 层/字段层函数 | 有效/无效节点 + 降级字段 |
| 4 | §4.2 E-DUP-ID | id 表去重判定 | 节点有效性终判 |
| 5 | §8.1 派生字段 | 行级正文计算 | chars / body_start / body_end |
| 6 | §7.2 边规范化 | derive 转置 + 折叠 | 规范化边集合 |
| 7 | §7 引用校验 | id 可解析性检查 | E-REF-NOT-FOUND 标注 |
| 8 | §6 软校验 | 声明层环检测 + 上游检查 | W-CYCLE-DECLARED / W-UPSTREAM-PENDING |
| 9 | §7.3 生效判定 | 双端 aligned 过滤 + 全局环检测 | 全局图 + E-CYCLE |
| 10 | §8.2–§8.4 输出 | serde 序列化 | ParseResult |

## 二、核心机制详解

### 2.1 节点边界识别（CommonMark 锚定）

**问题**：`# ` 出现在围栏代码块、容器块、1–3 空格缩进中时不构成节点边界。
**方案**：comrak 解析为 AST 后，仅取文档顶层子节点中的 ATX 一级标题（`setext == false`）作为边界；`sourcepos` 提供物理行号。
**验收**：围栏内 `# 通道配置`、引用块内 `# 伪标题`、缩进标题均不切分的 Fixture。

### 2.2 元数据三层校验（容错分层）

**问题**：元数据损坏方式多样，后果必须钉死且可预测。
**方案**：形态层（位置/前缀/单行/`-->` 残留）→ E-META-SYNTAX 节点无效；JSON 层（含重复键预扫描）→ E-META-SYNTAX 节点无效；字段层 → E-META-FIELD 逐字段降级（status→draft，坏边剔除，坏 id 走 E-MISSING-ID，坏 tags 忽略）。
**验收**：每层失败路径独立 Fixture，节点仍保留占位（invalid 标注）。

### 2.3 边规范化与延迟绑定

**问题**：derive 是 depend 的转置书写糖；未对齐结论不得进入全局图。
**方案**：derive 转置 → 三元组折叠（W-REDUNDANT-EDGE）→ 引用校验（E-REF-NOT-FOUND）→ 双端 aligned 过滤 → 全局图 SCC 环检测，循环边全集失效（E-CYCLE）。
**验收**：§10 示例全局图为空（concl-01 未 aligned）的数值吻合；环 Fixture 中仅循环边失效。

### 2.4 重复键检测（确定性保险）

**问题**：不同 JSON 解析器对重复键处理不一致（RFC 8259 未定义），破坏解析确定性。
**方案**：serde_json 之前以流式预扫描检测对象内重复键，命中即报 E-META-SYNTAX（节点级）/ W-DOC-META（文档级）。
**验收**：含重复键 Fixture 与 §3.1 行为表逐项吻合。

## 三、与生态的关系

### 3.1 组件边界

| 组件 | 职责 | 与本项目的关系 |
|---|---|---|
| Lodestone Protocol 规范 | 行为定义（源真相） | 本项目实现并验证之；实现不得反向篡改规范 |
| phyt-DNA 方法论 | 项目治理框架 | 本仓库 docs/ 即其物化 |
| comrak | CommonMark 0.31.2 块级解析 | 底座依赖，版本钉死（ADR-0001） |
| 消费方（AI agent / 工具） | L1/L2/L3 三级加载 | 本项目输出的 ParseResult 是其输入契约 |

### 3.2 使用方式

| 使用方式 | 说明 | 场景 |
|---|---|---|
| 库调用 | `mddag::parse(&str) -> ParseResult` | 嵌入 Rust 工具链 |
| CLI | `mddag <file>` 输出 JSON | 流水线 / 调试 |
| Golden Fixture | `tests/fixtures/` 即协议一致性语料 | 其他实现验证器对齐 |

## 四、不可替代性

规范、实现、测试三者在同一仓库闭环：规范改动若无 Fixture 背书不可合并，实现行为若与 Fixture 冲突即为 bug。这是"一个权威，多种呈现"中的那个权威。
